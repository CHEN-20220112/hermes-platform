1需求与定位

需求要点（按你最新描述归纳）：

① 仅管理员登录。平台不面向普通用户，只有一个（或少量）管理员账号，负责全部配置。
② 管理员配置"专家模型"。每个专家 = 不同的系统提示词 + 不同的 Skill + 不同的 MCP 工具（+ 模型选择），一个专家就是一套"人设 + 能力"的组合。
③ 接入飞书。平台把配置好的专家通过飞书开放给终端用户。
④ 飞书用户选择专家。飞书用户（无平台账号）在飞书中"选择不同的专家模型"来完成特定任务，例如选"数据分析专家"做报表、选"法务专家"审合同。
⑤ 平台只配置，执行靠 Hermes。平台本身不做推理、不跑 Agent 逻辑；真正的执行是 Hermes agent（加载管理员配置的系统提示词/Skill/MCP，调用底层大模型）。平台只负责"把配置交给 Hermes"和"把飞书请求路由到对应 Hermes"。

1.1 一句话定位

平台 = 管理员的"专家配置中心" + 飞书侧的"专家路由网关"；Hermes = 唯一的执行引擎。配置一次，飞书用户随时按需选择专家干活。

角色是否登录平台做什么
管理员是（唯一）配置专家（系统提示词/Skill/MCP/模型）、管理 Skill/MCP 仓库、接入飞书、查看审计
专家（Expert）否（配置单元）被配置、被飞书用户选择；对应一个 Hermes agent
飞书用户否在飞书里选择专家，下达任务，接收结果
Hermes agent否（执行引擎）加载配置、跑 Agent 循环、调用模型与工具，产出结果

2总体架构

三层：管理面（管理员后台）→ 路由面（飞书接入 + 专家路由）→ 执行面（Hermes agent 池）。平台承载管理面与路由面，执行面完全交给 Hermes。

管理面（管理员后台） 路由面（飞书+路由） 执行面（Hermes） 数据层
职责边界（重要）：平台不跑模型、不跑 Agent 循环。管理员配置的"系统提示词 / Skill / MCP / 模型"被平台渲染并下发到对应 Hermes Profile（SOUL.md / skills 目录 / config.yaml），Hermes 才是真正执行者。平台唯一在运行时做的事是路由：把飞书用户的请求导向所选专家的 Hermes 并把结果回传。

3角色与权限

角色登录权限
管理员平台账号（可做 MFA）全部：专家 CRUD、Skill/MCP 仓库、飞书接入、审计查看、专家启停
专家—非账号，是一个可被配置、可被选择的服务单元
飞书用户飞书身份（open_id）仅"选择可见的专家 + 对话"，无平台权限
  • 平台侧：管理员登录即可看到全部菜单；不需要多租户/角色矩阵，保持极简。
  • 飞书侧：权限靠飞书自身（FEISHU_ALLOWED_USERS 白名单、群策略、按用户 open_id 隔离会话）。
  • 审计：所有配置变更与调用留痕（谁改的、谁调的、用了哪个专家/Skill/MCP）。

4专家模型配置（核心）

一个"专家"就是一张配置卡，管理员在后台填写保存后，平台把它渲染下发为对应 Hermes Profile 的配置。

4.1 专家配置项 → Hermes 映射

管理员配置项示例下发到 Hermes 的位置
专家名称 / 描述"数据分析专家：负责报表与指标分析"Profile 描述（供飞书选择器展示）
系统提示词"你是一名资深数据分析师，先问清口径，再用工具取数…"Profile 的 SOUL.md（人格/系统指令）
模型 / 提供方anthropic/claude-sonnet-4 或自定义端点Profile config.yaml 的 model.default
Skill 绑定[sql 查询, 报表生成]Profile skills/<cat>/<skill>/ 目录
MCP 绑定[internal-db(白名单: 查询), github]Profile config.yaml 的 mcp_servers
飞书可见性启用 / 停用专家选择器是否展示

4.2 专家生命周期

  • 创建：后台新建专家 → 平台自动创建对应 Hermes Profile（hermes profile create <name> --description "..."）。
  • 编辑：改系统提示词 / 换 Skill / 换 MCP / 换模型 → 平台重写 SOUL.md / skills / config.yaml → 热加载或重启生效。
  • 启停：停用后从飞书选择器隐藏，且路由拒绝该专家请求。
  • 删除：停用 → 归档 → 清理 Profile（hermes profile delete）。

4.3 配置下发动作（平台 → Hermes）

# 管理员保存专家后，平台执行（伪代码）
render_expert(expert):
  1. 写系统提示词 → <profile>/SOUL.md
  2. 同步绑定 Skill → <profile>/skills/<cat>/<skill>/
  3. 合并 MCP + 模型 → <profile>/config.yaml (mcp_servers, model.default)
  4. 触发热加载（API Server: /skills reload；gateway 模式: restart）
  5. 回读校验（skills_list / doctor）确认生效

5Skill 配置管理

Skill 复用 Hermes 原生规范（SKILL.md + YAML frontmatter + 可选 references/scripts，兼容 agentskills.io）。平台维护中央仓库，管理员把 Skill 绑定到不同专家。

中央仓库统一存储与索引；支持在线编写或上传；AI 自动生成的 Skill 可回流入库。
版本与审核简单 semver；编辑后标记版本；可回滚到上一版。
专家绑定在专家配置页勾选 Skill → 平台同步到该专家 Profile 的 skills 目录。
生效策略保存即下发；不覆盖 Hermes 本地被修改过的 Skill（冲突保护）。

5.1 SKILL.md 形态

---
name: sql-query
description: 针对内部数仓执行只读 SQL 查询并格式化结果
version: 1.2.0
metadata:
  tags: [sql, database]
  category: data
requires_toolsets: [terminal, file]
---

6MCP 工具配置管理

管理员在平台登记 MCP Server（工具来源），再把 Server（含工具过滤策略）绑定到专家；凭据统一托管。

模块说明
Server 注册stdio 型（command/args/env）与 HTTP 型（url/headers）统一登记，存配置模板
Secret Vaulttoken/凭据加密托管；下发注入 env，日志不落明文
工具过滤每个专家可对每个 Server 设置 tools.include/tools.exclude（默认白名单）
专家绑定在专家配置页勾选 Server + 过滤策略 → 合并进该专家 config.yaml 的 mcp_servers
健康检查连通性探测、工具清单校验、调用审计

6.1 下发后 config.yaml 形态

mcp_servers:
  internal-db:
    url: "https://mcp.internal.corp:8443/mcp"
    headers:
      Authorization: "Bearer ***"        # Secret Vault 注入
    tools:
      include: [list_datasets, run_sql_query]   # 只读白名单
    enabled: true
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "***"
    tools:
      exclude: [delete_repo]

7飞书接入与专家选择

飞书用户是最终使用者。核心交互是"选专家 → 干活"。

7.1 接入模式

模式 A · 单机器人 + 平台路由（推荐）：平台统一持有 1 个飞书 App，用户私聊/群聊 @ 机器人 → 平台发专家选择卡片（列出所有可见专家）→ 用户点选 → 平台路由到该专家的 Hermes 执行。一个机器人服务所有专家，能力统一、白名单统一。
模式 B · 一专家一机器人：某专家需要独立机器人身份（如对外部门专属机器人）时，平台为其单独配置 App 并托管 gateway。适合"每个专家独立对外"的场景。

7.2 专家选择机制（模式 A）

方式用户操作实现
推荐 交互卡片@机器人或发"专家" → 收到卡片 → 点选飞书卡片按钮回调 → card.action.trigger → 平台路由
指令路由直接输入"用数据分析专家：本周销量"消息解析"专家名:"前缀 → 命中即路由
会话记忆选过一次后默认保持该专家，可切换按 用户+专家 维度保存 session 映射

7.3 会话与隔离

  • 会话键 = 用户 open_id + 专家：不同用户之间隔离，同一用户切换专家后上下文不串。
  • 群聊：@机器人 才响应；按群 + 按用户隔离（对齐 Hermes group_sessions_per_user: true）。
  • 消息去重（message_id，24h TTL）、突发批处理、typing 状态。
  • 安全：FEISHU_ALLOWED_USERS 白名单、群策略、webhook 模式签名校验、限流。

8两条链路：配置流 & 运行时流

8.1 配置流（管理员操作，低频）

管理员                    平台后台                Hermes Profile
   │ ① 创建/编辑专家（提示词/Skill/MCP/模型）        │                │
   ├───────────────────→ ② 生成渲染配置               │                │
   │                      │ ③ 写 SOUL.md / skills / config.yaml          │
   │                      ├────────────────────────────────→ ④ 加载配置
   │                      │ ◀────────────────────────────────  ⑤ 生效确认
   │ ◀─────────────────── ⑥ 保存成功，专家上线            │                │

8.2 运行时流（飞书用户操作，高频）

飞书用户                  飞书机器人/平台            Hermes（所选专家）        底层 LLM
   │ ① 选择专家（卡片/指令）                            │                    │
   ├───────────────────→ ② 路由到专家 A 的 Profile      │                    │
   │ ③ 发送任务（含附件）   │                            │                    │
   ├───────────────────→ ④ 组装（会话+已下发能力）        │                    │
   │                      ├───────────────→ ⑤ API Server/CLI 调用          │
   │                      │                │ ⑥ Agent 循环（Skill/MCP/工具）   │
   │                      │                ├──────────────────→ ⑦ 模型推理
   │                      │                │ ◀──────────────────  返回
   │                      │ ◀─────────────── ⑧ 结果（流式）               │
   │ ◀─────────────────── ⑨ 渲染回复/文件/卡片            │                    │
   │                      │ ⑩ 审计/用量入库               │                    │

11实施路线

M0
平台后台骨架 + 管理员登录 + 专家 CRUD1 周

管理员登录；专家表与配置页（系统提示词/模型/Skill/MCP 绑定表单）。

M1
专家配置下发到 Hermes1~2 周

平台创建 Profile、渲染写 SOUL.md/skills/config.yaml、热加载、回读校验；用 2~3 个示例专家验证"配置即生效"。

M2
Skill / MCP 中央仓库1~2 周

Skill 仓库（编写/上传/绑定）；MCP 仓库（注册/Secret/过滤/绑定）；绑定变更自动触发下发。

M3
飞书接入 + 专家选择1~2 周

模式 A：单机器人 + 专家选择卡片 + 指令路由 + 会话隔离 + 富文本/文件回复，闭环"选专家 → 干活"。

M4
审计 / 用量 / 运维1 周

调用审计、token 用量与成本报表、专家健康监控、灰度启停。

M5
扩展持续

一专家一机器人（模式 B）、多飞书 App、专家市场、多机 Fleet。

12风险与关键决策

风险 / 决策点建议
专家与 Profile 的生命周期一致性专家创建/删除与 Profile 创建/删除绑定为事务；删除前先停用归档
系统提示词更新生效SOUL.md 新会话生效；告知"切换新会话后生效"，必要时强制重置该专家会话
Skill 被 Hermes 升级覆盖hermes update 会同步内置 Skill；平台记录"本地修改"标记并合并去重
会话隔离严格按 用户+专家 隔离；切换专家/用户不串上下文（Hermes API Server 按会话隔离）
专家数量与资源每个专家一个常驻 API Server 进程较耗资源；低频专家可"按需拉起/CLI 兜底"，空闲休眠
凭据安全App Secret / MCP token 只入 Vault，日志脱敏，定期轮换
飞书用户误用敏感工具每个专家默认最小工具面（MCP 白名单）；高危操作走交互卡片二次确认
一句话总结：平台 = 管理员配置中心 + 飞书路由网关：管理员在后台配置"专家"（系统提示词 + Skill + MCP + 模型），平台将其渲染下发为对应 Hermes Profile；飞书用户选择专家后，平台把请求路由到该专家的 Hermes agent 执行（Hermes 调用底层模型），结果回传。平台不执行，执行永远在 Hermes。
